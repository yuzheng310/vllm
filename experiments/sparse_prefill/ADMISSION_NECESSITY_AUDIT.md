# 多轮 rollout 显存感知准入：开发前必要性审查

审查日期：2026-09-14。结论：**当前不立项，不修改调度器，不启动 GPU 实验。**

用户要求先证明真实需求与开发必要性，不能为简历先做功能再补场景。
本次审查使用本地项目代码、原版 Git 快照和已有实验报告；没有进行性能测试。

## 场景存在，但待解决的瓶颈没有被证明

RepoCompass 的确运行多轮代码定位 RL rollout。生成入口把同轨迹请求带上
session_id，以便在同一引擎复用前缀。4B 脚本使用 vLLM、异步引擎、最长十轮，
输入长度上限 40960，采样输出上限 8192。脚本参数可以被启动参数覆盖。

来源：[生成入口](../../../repocompass/src/generator/code_search_generator.py)、
[训练脚本](../../../repocompass/scripts/run_async_training_4b.sh)。

不能从 batch_size、n_samples_per_prompt 或最大长度推断某时刻的显存压力。
工具等待、不同轨迹进度、引擎路由和外层准入都会改变同时驻留的请求。
当前审查未找到足以建立必要性的原生 vLLM 实际部署记录：有效并发时间线、
KV 池容量、抢占次数、可避免重算的耗时及其对整批 rollout 完成时间的贡献。
这里的“未找到”只限本次检查的文件，不是声称整个工作区没有任何日志。

此外，RepoCompass 的 pyproject.toml 固定 `vllm==0.11.0`，本实验 fork
基线是 v0.29.0。这是必须单列的集成差异：尚未证明新版本已用于当前训练。
旧版本集成与新版本引擎之间不能直接转移瓶颈、接口兼容或性能结论。

## 提议与原版现成功能显著重叠

使用 `git show` 核对未修改的基线 v0.29.0 快照
`98dff2a81d747d1dba01a47f939f48c3526d4206`，避免把 fork 修改误当上游能力。

- `vllm/config/scheduler.py`：`scheduler_reserve_full_isl=True`，
  准入时检查完整输入的容量需求，避免分块 prefill 只看第一块而过量准入。
- 同文件 `watermark`：提供准入时保留空闲 KV 块的水位参数，默认 0。
  其注释明确指出目标是减少显存紧张时反复抢占。
- `vllm/v1/core/kv_cache_manager.py` 的 `allocate_slots`：
  完整输入需求计算考虑已有前缀命中与相应缓存布局；需要的块加水位超过
  可用块时返回 None。水位对已存在运行请求时的等待/抢占请求适用。
- `vllm/v1/core/sched/scheduler.py` 的等待队列准入实际调用这些接口；
  分配失败时不会把该请求加入本轮运行。
- `reserved_blocks` 还处理异步外部 KV 加载的在途预留，但这不能描述为
  所有普通生成请求都已按未来最大输出完整预留。

因此，“看剩余 KV、考虑已有缓存、按输入长度决定是否接纳”不是当前基线
缺失的功能。完整输入准入也不保证未来 decode 或新一轮工具输出不会增长。
未来长度未知是剩余问题，但当前没有证明预测机制会优于已有水位和并发参数。
不能用旧集成版本缺少某项能力，作为在新版本重复开发已有能力的理由。

## 既有实验同时包含正面和否定证据

[自研运行时调优报告](../../../../personnalinfra/qwen3-runtime/docs/session_cpu_offload_tuning.md)
记录容量受限时确有重算，以及独立任务集调低活跃并发后更快的结果。
同一报告也记录特定 4 客户端设置下，实测总前向 token 数等于不重复处理
该轨迹所需的数量，没有可消除的历史重算，CPU 恢复次数为零。

这些结果使用自研引擎、特定容量和合成工具等待，不能视为原生 vLLM 的
生产瓶颈。报告中的 4 并发来自该 adapter，不能直接套到 RepoCompass 的
vLLM 后端；24 客户端结果也不能包装为当前默认训练收益。

一张 24GB 卡可能有压力，但物理显存数字本身不能证明有必要设计新调度。
反过来，48GiB 特定配置无重算，也不能证明 24GB 永远没有问题。

## 第一性原理与机会成本

目标应是同一批实际 rollout 更早完整结束，而非只使抢占计数下降。
减少并发可能降低 GPU 批处理效率；保守预留未来输出会闲置显存；优先短任务
可能拖慢长轨迹。异步 RL 中完成顺序还可能影响策略版本滞后和样本进入训练
的顺序，不能只比较重算 token 数就宣布完整训练等价。

在只删除重复工作的简化模型下，若该工作占目标耗时的比例为 f，理想加速比
上限为 1/(1-f)，耗时降低上限为 f。这个模型要求 f 是目标耗时中可消除的
贡献，不能直接用重复 token 比例或请求耗时总和替代。当前连这个 f 的可靠
估计都没有，无法宣称“大概率有大收益”。

## 重新立项必须有的新证据

1. 实际 vLLM 配置和请求时间线显示存在占比可观的额外重算。
2. 已有完整输入准入、水位、并发及批 token 参数仍不能合理解决。
3. 指出一个现有机制无法利用的具体信息或状态，并推导它何时带来净收益。
4. 定义可在单卡验证的完整工作负载、强基线和副作用边界，不人为压缩缓存或
   放大并发来制造故障；资源受限的扩展场景必须与当前部署结果分开报告。

在这些条件得到支持前，该提议停止于源码与必要性审查。获取已有部署证据或
必要的最小基线观测属于诊断，但不是先实现功能再找收益的许可。

## 对先前评分实验的定位更正

评分实验的数值与耗时记录保留；其假设是固定 reference 的增量概率计算。
RepoCompass 当前训练脚本关闭 KL，特定 GSPO 路径合并行为概率前向。
没有建立独立逐轮 reference 评分的真实需求，也没有验证蒸馏或完整训练收益。
撤回将该实验直接作为 RepoCompass 核心优化成果的推荐，不因已有代码投入
而新增不需要的训练环节。之后选题以真实需求和上游缺口为先。
