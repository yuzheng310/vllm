# 两轮实验之后：还有什么值得作为 vLLM 二开

后续执行结果（2026-09-14）：用户批准下述唯一补证后，真实 Qwen3-4B
完成七轮回放。相对匹配实际 KV 容量的较强原版，剩余耗时优势约 2.70%，
未达到 10% 门槛，停止此方向。见 [完整结果](../session_affinity/RESULTS_4B.md)。
以下保留实验前的推导和当时状态，不再视为一项待执行建议。

日期：2026-09-14。此次仅重新核算已保存数据并阅读实际调用链，没有连接
实验机、启动 GPU 或新增性能实验。所有数值区分既有实测、离线字节核算
和容量推导，不能合并成一个新的加速成绩。

## 决策

优先项是**将已经实现的会话续跑调度，补到目标 4B 的容量条件下判断**。
目前没有另一个同时具备真实需求、原生缺口和显著任务级收益的新功能。
目标 4B 尚未测，不能称已找到可作为主成果的收益；但用 0.6B 的可替代
结果否定整个方向也过早。继续的理由是明确的模型/容量差异，而非换参数
碰运气。现有移植和冻结数据可以复用，不需先开发另一套调度器。

依据见[独立调用链审查](REAL_WORKLOAD_EVIDENCE_REVIEW.md)和
[原始数据重算](existing_results_reanalysis.json)。

## 两轮结果给出的具体信息

| 方向 | 已有实测 | 对当前需求的判断 |
| --- | --- | --- |
| 稀疏评分 + 安全前缀复用 | 特定两条评分回放快 53%–60% | 当前 GSPO 不执行该独立评分，不能补造训练环节来兑现数字 |
| 会话续跑调度，0.6B、c16 | 整批约 60.1→53.5s，快约 11% | 对应真实多轮生成阶段；机制成立，但原版 c8 已到 54.7s |
| 原版 c16→c8 | 原版整批减少约 8.9%，单轮 c8 对照 | 可作原生配置调优证据，不能叫新增 vLLM 功能，也未验证最优配置 |
| CPU KV offload，既有自研引擎 | 部分压力点获益，默认低并发零恢复/零重算 | 与此次原版 c8 反证相呼应；不应再重新实现留存来寻找同一块收益 |

## 新核算：原版 c8 究竟追回了什么

48 条冻结轨迹有 233 次请求，其中 185 次是后续轮。逐一验证实际 input IDs，
185/185 都以其上一轮 input IDs 为严格前缀。按当前默认 16-token block
对齐，只考察上一轮输入，不把本次生成内容当成下一轮历史。

| 已有回放 | 命中 token 总数 | 丢失上一轮整块输入的请求 | 对应缺失 token 数 |
| --- | --- | --- | --- |
| 原版 c16，A1/A2 相同 | 1,801,664 | 30/185 | 182,368 |
| 候选 c16，B1/B2 相同 | 1,984,032 | 0/185 | 0 |
| 原版 c8 | 1,984,032 | 0/185 | 0 |
| 候选 c8 | 1,984,032 | 0/185 | 0 |

这比“二开只比调参快 2.2%”更有解释力：在 0.6B 上，原版 c8 和候选 c16
消除了同一份历史重算。不能再指望缓存 pin、回收已结束会话或 CPU 备份
在该对照上省掉这部分工作。这不是所有共享前缀的全局计算下界，也不包含
历史输出与实测生成输出不同所造成的边界；没有推出所有缓存研究均无意义。

该结果也解释为何不能把长输入/短输出直接翻译成 prefill 主导耗时：
缓存命中后，仍需逐 token 生成动作。旧日志的 queued/prefill/decode 是
请求阶段驻留时间，并发请求互相重叠，不能把它们相加后当 GPU 算子占比。

## 为什么真正的 4B 仍值得一项有边界的补证

0.6B 正式日志中的 KV 池是 **162,752 token**。日志封存在
`../session_affinity/results/run-logs.tar.gz` 的
`reports/session-release-06b-c16-a1.log`。

目标 4B 结构为 36 layers、8 KV heads、head_dim=128，BF16：

`KV bytes/token = 2 × 36 × 8 × 128 × 2 = 147456 bytes = 144 KiB`。

精确参数权重约 7.493 GiB，远高于 0.6B 日志的约 1.31 GiB
weights + non-torch 占用。按该日志 desired 18.81 GiB 的预算，
只扣 4B 权重，KV 上限约 **82.4k token**；若直接按 nvidia-smi 的
24564 MiB × 0.8 计算，约为 **85.2k token**。两者口径不同，都尚未扣
4B 工作区、激活、图和其他开销，不能当作真实引擎分配。可靠结论只是
“4B 的容量量级约为已测 0.6B 的一半”，实际值仍待目标引擎启动报告。

由此形成尚未回答的问题：

1. 0.6B 的 8 会话能保住历史，4B 的 8 会话未必能保住。
2. 原版若进一步降会话并发，可能同时减小有效 decode batch；4B 每步
   权重读取更大，较小 batch 的权重成本摊销可能更差。
3. 已有调度改动可能在较高会话并发下保留历史复用，缓解上述冲突。

第 3 点必须验证，不能由前两点保证：缓存可能在请求返回前就丢失，
较高并发可能根本装不下，新增输入可能才是主要成本，原生调参也可能
再次胜出。没有提前给出 4B 收益百分比或成功概率。

因此选择的是一个已由 0.6B 正反实验约束的具体问题，不是泛化的
“多轮调度优化”。场景是现有 RL rollout 的多轮搜索/读代码；最终可写的
指标应是相对合理配置原版的固定任务集耗时/轨迹吞吐，而非命中率或代码量。

## 发现但不作为新主课题的重复 token 数据

当前链路每轮要求 `return_token_ids=True`。GPU 命中 KV 并不会自动省掉
HTTP 返回的完整 prompt ID 列表；RepoCompass 已有的压缩在 Conversation
结束后的 Ray 返回边界，未消除逐轮响应。

对同一冻结输入做精确离线编码，保留首轮全量、后续只编码相对上一轮
input 的新增 IDs，并加入起始偏移字段，所有请求都可逐 token 恢复：

| 仅 prompt-ID 字段的编码 | 全量 | 假设的增量编码 | 减少 |
| --- | --- | --- | --- |
| token ID 个数 | 2,661,314 | 820,992 | 69.15% |
| 紧凑 JSON 字节 | 12,062,893 | 3,723,683 | 69.13% |
| 逐响应字段各自 gzip 后字节 | 2,972,114 | 971,654 | 67.31% |

这些是**假设协议的离线字段体积**，不是实测 HTTP 流量或速度。不含
完整响应、请求、协议头及 base-ID/hash/回退元数据，不能写成系统流量
已下降 69%，更不能写成 rollout 提速 69%。

更重要的是，固定 SkyRL 已有“获得响应字典→JSONResponse”的边界，
可以在那里做同样的增量编码，无需改 vLLM 核心。因此它可作为后续
RepoCompass 数据通路优化候选，但不能用其字节数字支撑“必须二开 vLLM”。
现有 `usage` 不能替代精确 token 身份，原生单次 streaming delta 也不等于
跨工具轮次的 prompt delta；这些接口边界已在独立审查中分别核对。

## 若继续，仅补以下缺口

- 使用目标 4B checkpoint，保留同一 48 轨迹、233 请求和完整生成长度。
  Qwen3 基础权重与 CodeScout 后训练权重必须分别标注，不能冒称同一模型。
- 源码不再新增策略。先检查 4B 实际分配与原版 c8 的历史重算；容量差异
  使 c4 成为有依据的强原生对照，比较候选 c8 与原版 c4/c8，保留所有结果。
  不扩展并发/工具等待参数网格。若原版 c8 已完整命中，不再用缓存理由继续。
- 沿用已冻结的阈值规则：由原版 c8 排队中位数向上取整到秒，在候选之前
  决定；不是看到候选成绩后选秒数。正向结果才重复交替验证。
- 只有超出较快原生对照的剩余收益达到既定 10% 耗时门槛，且尾部/完成率
  可接受，才进入简历主成果候选。输出和质量边界仍分别披露。
- 真实集成还缺 session ID 转发：当前 SkyRL 会 pop 该字段用于路由，
  直接引擎回放不经过这条链路。接入时应补字段传递，不能把该修复单算收益。

此次没有执行上述 GPU 工作；它是根据已有数据收窄后的唯一优先问题。
若仍被原生合理配置追回，就保留负结果，不再把当前缓存方向升级包装。
