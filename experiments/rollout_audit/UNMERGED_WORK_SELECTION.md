## 为什么第一项对应真实 RL 场景

RepoCompass 的工作是“查看代码 → 调用搜索/读文件工具 → 再看结果 →
继续定位”。这是 RL 的轨迹采集阶段；优化目标是单位时间完成更多可交给
训练端的轨迹，不改变 reward、训练 loss 或引入额外概率评分服务。

本地依据：

- `src/generator/code_search_generator.py:151–160` 已给每条轨迹附带
  session_id，用于多轮请求保持引擎亲和性。
- `scripts/run_async_training_4b.sh` 默认 batch 8、每题样本 8、async engine
  开启。客户端配置并不等于引擎实际排队并发，不能直接将其当压力测量。
- 公开代码定位评估轨迹是长输入、短动作：输入中位数 9981 token，输出
  中位数 87 token。详情与数据边界见 [README](README.md)。
- 既有冻结前缀重建分析的 1901 个相邻轮次均为 append-only，可复用 token
  中位数 7473；该统计是结构上可复用，不是当前引擎实测命中率。

直观例子：任务 A 刚读完一个文件，回来继续问模型。它前面已经处理过的
长历史还在 GPU 缓存里。队列里还有先到的新任务 B。若先跑 B，它的新输入
可能挤掉 A 的缓存；轮到 A 时，就需要重算原本能复用的历史。
候选策略在有限范围内让 A 先续跑，尽量在缓存被挤掉前用上它。

这里没有锁住 A 在整个工具执行期间的 KV，也不保证所有 A 都提前。
必须是 A 已返回并入队、近期同会话、且当下查到真实本地缓存命中，才是候选。
若只剩一个请求、所有候选均无缓存、或队首等待达到阈值，就没有这种调整。

## 原生能力和新增能力的边界

本轮读取当前 main SHA：
`dfa1984e58dc898610a320de26f94b6039fccec3`。
[该版本调度配置](https://github.com/vllm-project/vllm/blob/dfa1984e58dc898610a320de26f94b6039fccec3/vllm/config/scheduler.py)
内置 policy 为 fcfs / priority，支持 custom scheduler，未包含该会话策略；
调度目录也没有 SessionAffinityScheduler。

原生 APC 已经会复用缓存，full-input admission / watermark 已考虑显存
准入。新增点是依据引擎实际缓存状态，自动调整等待请求的执行顺序。
“是否装得下”和“多个可执行请求谁先跑”是不同决策。
外部 priority 可以手动设顺序，但不等于内置了这套实时本地缓存判断与退让。

检索也找到已合并的 [PR 10128](https://github.com/vllm-project/vllm/pull/10128)：
2024 年 V0 的 prefix-aware scheduling 修正 token budget 对 cached tokens
的计数，不能据此宣称缓存感知调度从未有人做过；也不能将它等同本候选的
有界会话续跑重排。我们的表述必须明确到策略与版本。

## 第一性原理：收益成立条件和风险

单纯更改排队顺序，不保证减少整批工作的计算量。收益需要至少出现以下
机制之一：及时利用本会被淘汰的缓存，或改善有效 batching / 多轮任务推进。
前一种机制的净收益可理解为“避免的历史重算成本减去查缓存与重排开销”。
只提高命中率、只缩短热请求等待而拖慢冷请求，都不是完整成功标准。

因此存在明确的无收益边界：无排队、缓存充裕且原本不会丢、工具等待主导
整个任务、缓存已在工具执行中被完全淘汰。不能通过人为挤小 KV 容量制造
唯一正例，也不能把高压力回放结果泛化成当前所有训练配置的收益。

代码审查需处理的具体事项：

1. 最小可移植范围是新增调度类、无副作用缓存查询、配置和参数传递。
   118 行核心代码不等于整个集成只需 118 行；当前 RepoCompass 固定
   vLLM 0.11.0，实验 fork 为 0.29.0，版本衔接需要单独确认。
2. session_id 必须真正经过代理传到 engine Request；客户端有字段不代表
   服务端接收完整。跨权重版本仍必须遵循原生缓存失效，不能跨版本复用。
3. 最大队首等待阈值只是停止重排条件，不是请求完成时间的硬上限。
   作者 30s 参数不能原样当作本项目公平性承诺。
4. 当前实现明确检查 PREEMPTED 队首；PR 正文“preempted requests are
   never bypassed”的更强说法，还需结合队列不变量核对非队首情形。
5. 候选未被真正调度时会恢复位置；恢复时的 successor、skipped queue、
   async 状态转换需要核对。缓存查询不能分配块或重复发送 KV event。
6. 排序改变 batch，浮点归约与采样结果可能变化；不能仅因未改模型权重就
   宣称输出逐 token 恒等。有限队列窗口与会话 TTL 也引入 CPU 开销。

主要结果应为完整轨迹吞吐、固定任务集墙钟、轨迹 P95 和完成率；引擎
缓存命中/重算仅解释原因。安排正常场景与无压力对照，不以某个极端压力
单点过关。真正 RL 训练吞吐还包含工具、训练和权重同步，单卡 rollout
回放不能宣称训练加速或收敛提升。
