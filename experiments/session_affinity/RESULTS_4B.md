# 4B 容量对照：未达到继续投入门槛

2026-09-14。**停止当前方向的 GPU 测试，不推荐作为主要简历收益。**
相对本轮测到的较强原版，48 条轨迹整批耗时为 166.548→162.046s，
仅下降约 **2.70%**，低于事前固定的 10% 门槛。这是一次配对观察，
不足以宣称稳定的 2.7% 加速。不是完整 RL 训练，不报告 reward 或定位质量。

## 实验范围

真实 Qwen/Qwen3-4B BF16 基础权重，单张 RTX 4090 D 24GB。
这不是 CodeScout 后训练 checkpoint。三片权重按固定官方清单验证 SHA256，
见 [权重清单](results_4b/weights-manifest.json)。
48 条冻结公开代码定位轨迹、233 请求、22,046 个生成 token；后续输入仍取
历史轨迹，不由当前输出驱动真实工具。轮间 0.25s 为披露的模拟间隔。

原版是未修改的 v0.29.0，SHA `98dff2a81d747d1dba01a47f939f48c3526d4206`。
候选延续 PR 51384 的移植和已记录的本地修正，本轮没有改变调度算法。
各轮候选提交不同，仅因增加执行、对照和记录文件；加载源码 SHA 逐轮留档。
直接 AsyncLLM 回放未接通真实 SkyRL 的 session ID 转发和训练循环。

同卡顺序运行，OMP=1、max_num_seqs=8、batch tokens=2048、GPU预算0.8，
APC/chunk/async 开启。每次新进程加载模型，预热后清空 APC，再计整批时间；
启动/JIT 单独留档。c4/c8 指同时活动的完整轨迹数，不是修改 max_num_seqs。

每轮均完成 48/48 轨迹、233/233 请求，无 corrupted 标记。只有首个原版
c8 出现一次抢占，其余为零。开启自动选择表示允许引擎按条件采用 cascade，
未逐算子证明每次前向均使用该内核。

主确认顺序 A1/B1/B2/A2 的双方实际 KV 池相同。两次中位数约
180.088→161.980s，耗时下降 **10.06%**，轨迹吞吐增加 **11.18%**。
这个数字相对原版 c4 的指定配置成立；它不能代表相对较强原版的收益。
后续相同 c8、相同自动选择设置、相同 79,424-token 池的对照，剩余耗时
优势只有 4.502s，即 2.70%，轨迹吞吐约 17.29→17.77 条/分钟。
没有通过强对照，不再扩展并发、工具等待或让行阈值参数网格。

候选让行阈值 1s 来自首个原版 c8 的排队中位数约 5.16 微秒，按事前规则
向上取整，在候选开始前记录。强原版队列中位数约 4.50 微秒，按同一规则
仍为 1s；没有看候选收益后调阈值。FCFS 不使用此参数。

## 发现的资源混杂与解释修正

相同 gpu_memory_utilization 并未保证相同实际 KV 容量。首次原版 c8
分配 69,984 token / 9.61 GiB，日志中的 weights + non-torch 为 8.39 GiB，
峰值 activation 为 0.80 GiB。之后六轮均为 79,424 token / 10.91 GiB，
对应 7.69 GiB 和 0.21 GiB。预算同为 18.81 GiB，图内存同为 0.03 GiB。
逐轮记录与日志指纹见 [容量审计](results_4b/capacity-audit.json)。

差异与首次编译及后续编译缓存复用同时出现，但没有隔离其具体原因。
因此不能把原版 180.731→166.548s 全部归于 cascade，也不能把初筛 c8
和候选的差距全部归于新调度器。c8→c4 的命中差异同样混有池容量变化。
这些初筛数字保留为观察，撤回纯单因素解释。

最终强对照双方实际容量和自动选择设置一致，不受上述跨组混用影响；
A/B/B/A 的池容量也一致。既已不达继续投入门槛，不再追加 GPU 诊断去
分离首次内存剖析差异。分析脚本将实际 KV 容量纳入可比条件。

## 机制成立不等于主要目标达成

匹配资源的 c8 强对照中，候选比原版少缺失 34,320 个上一轮整块输入 token，
有缺失的后续请求由 21 降到 17；但整批只省约 4.5 秒。改善缓存复用的
空间存在，实测收益量级不足以支撑本项目要求。没有把请求阶段驻留时间
相加当成 GPU 算子时间，也没有测得可精确归因的重算耗时占比。

原版 c4 没有上一轮整块输入缺失，却慢于仍有缺失的候选 c8，说明缓存
命中不是最终目标；并发改变也会改变批处理与等待。未分别测量这些成本，
不将差额全部归因为某个算子或带宽。本轮结果不代表所有工作负载都无收益。

## 延迟、输出与未执行的检查

批次完成 P95 从所有任务可用的统一批次起点计算，纳入外部任务池等待。
原始 trajectory_active_p95 只计活跃时间，两者不能混用。
强对照的冷首轮 P95 为原版 11.890s、候选 11.299s；请求 TTFT P95 为
3.474s、2.970s。候选仍高于低并发原版 c4 的约 5.753s、1.947s，
不能声称所有交互延迟都改善。

相同资源和默认数值模式下，强对照完整输出序列仅 **143/233** 请求相同。
候选 B1/B2 自身重复为 207/233，原版 c4 A1/A2 为 222/233；存在数值和
生成差异，完成率、corrupted 标记不能代替 Agent 任务质量评估。
此前初筛跨容量比较的 140/233、125/233 不再当作匹配资源的正确性证据。

4B batch-invariant 对照脚本已准备，但**因性能门槛失败未执行**。
0.6B 的 233/233 一致不能借用为 4B 证据，也不能拼接“10% 无损提速”。
未修改简历，未将个人 fork 说成上游合并贡献。用户要求的主要简历收益
尚未达成；代码、测试、归档数量不是替代收益。
