# 目标 4B 的唯一补充对照

2026-09-14，在任何 4B 推理之前固定。沿用
[基于已有数据的决策](../rollout_audit/POST_EXPERIMENT_SELECTION.md)。

- 模型是 Qwen/Qwen3-4B 的真实 BF16 基础权重，不冒称 CodeScout checkpoint。
  三片权重须通过原固定 HF/ModelScope 清单的完整 SHA 检验。
- 输入仍为同一冻结的 48 条轨迹、233 请求；生成完整记录长度，工具间隔
  仍为 0.25s，不改变任务、截断长度或提高压力。它是回放而非真实 RL。
- 基线仍为干净 v0.29.0，候选已有调度实现不变；相同依赖、OMP=1、
  max_num_seqs=8、batch tokens=2048、GPU utilization=0.8、APC/chunk/async
  开启。沿用原回放的 cascade 关闭配置，故不称穷尽原版所有最佳设置。
- 首先原版 c8；如果后续请求已经完整命中上一轮整块输入，就停止缓存
  假设。否则运行原版 c4，再运行候选 c8；c4 来自容量约减半的先验推导。
- 候选 max_wait 取原版 c8 请求排队中位数向上取整到秒；在候选运行前落盘。
  不按候选结果调参。每项初筛只运行一次，正向结果才增加交替重复。
- 相对 c4/c8 中更快的原版，整批耗时至少下降 10% 才进入复测。
  48/48 任务、233/233 请求必须完整；尾部需要检查，不能只看均值。
- 比较不同客户端并发的轨迹 P95 时，使用从统一批次起点到完成的时间，
  把任务尚未被 worker 领取的等待包括在内。只计活跃执行时间的 P95
  可在同为 c8 的对照之间比较，不能因 c4 把排队移到引擎外就认为尾部更好。
  复测准入以候选完成时间 P95 不比更快原版恶化超过 5% 为边界；同时披露
  冷首轮与请求 TTFT，而非将它们隐藏在吞吐指标内。
- 若得到正向结果，另核对保持原生 cascade 自动选择后的强对照，避免
  将固定关闭一个原生优化的卡片称作生产最佳收益；未通过不增加参数网格。
- 默认模式输出可能因 batch 变化而不同；不能预告逐 token 等价。只有
  值得复测的性能结果才补目标模型的确定性正确性检查，分别报告模式，
  不跨模式拼接“无损提速”，也不把回放完成率称作 reward/定位准确率。

`run_4b_screen.py` 只负责按上述顺序运行已有 replay、核查干净源码及权重
哈希、记录命令与派生阈值。它拒绝覆盖已有输出，每个 arm 最长 20 分钟。
仍经远端 `run-in-workspace.sh` 设置所有缓存和驱动路径，不改共享系统。
GPU 进程占用检查由每次 replay 在模型加载前执行。

## 执行后的结果注记

上述协议先于实验固定，未因观察到的收益调整。七轮回放完成后，匹配实际
79,424-token KV 池、同为 c8 和原生 cascade 自动模式的对照，仅观察到
2.70% 耗时下降，故停止，不执行预备的 4B 确定性对照或继续扫参数。
复核还发现首次原版 c8 的实际池只有 69,984 token，相同 utilization
不是实际容量相同的证明；该跨容量结果不作纯调度或纯 cascade 归因。
原始初筛判断保留，最终判断以 [RESULTS_4B.md](RESULTS_4B.md) 为准。
