# 会话续跑调度：单卡验证

状态：2026-09-14，已经移植并通过调度/缓存测试，性能结果尚待验证。
来源是 [vLLM PR 51384](https://github.com/vllm-project/vllm/pull/51384)，
固定 head `ffab744661e35e5dd5057155210adaaaaaeb75ab`。
原始移植提交 `4c1bf31` 保留两位作者归属；`b82e9ef` 单独记录我们的
恢复请求边界修正、评分缓存兼容及回放工具。没有新开重复的上游 PR。

## 要回答的问题与预先约定

真实目标是减少多轮代码定位 rollout 的完整轨迹完成时间。
本试验固定历史输入与生成长度，隔离推理调度；不运行反向传播、工具环境
或权重更新，不宣称训练吞吐或 reward 改善。

- 先用已有真实 Qwen3-0.6B 权重做 2 条轨迹的功能检查，不把它当 4B 成绩。
- 目标模型为真实 Qwen3-4B BF16，所有权重文件按官方固定清单验证 SHA256。
  0.6B 与 4B 的结果分别标注，不用 dummy 权重替代。
- 两侧都开启 APC、chunked prefill、async；max_num_seqs=8、
  max_num_batched_tokens=2048、gpu_memory_utilization=0.8、max_len=40960。
  正式对照保留默认编译/CUDA graph，不把 eager 功能检查当正式性能。
- 48 条任务按 instance_id 的 SHA256 顺序选择首批符合完整长度限制的
  轨迹；不看运行结果挑任务。本次 233 个请求，无须跳过超长任务。
- 冻结输入 SHA256 为
  `e5394db91afad03820a87f7b3ad6ec94339e57e1631951902e35ad7a859c0703`。
  原 parquet 和 tokenizer 版本写在工作负载内；公开日志没有工具耗时，
  所以轮间统一 0.25s 是披露的模拟参数，不冒称真实时间线。
- 主要并发 16，正常负载对照并发 8；不缩小 KV 内存制造唯一正例。
  同一张卡顺序运行，启动时检查是否有其他 GPU 计算进程。
- 首先比较 FCFS 与作者用于报告收益的 max_wait=30s。这个参数仅用于
  检验作者机制，不是产品公平性承诺；默认 0.5s 作为保守策略对照。
  不扫参数网格。若首轮没有有意义收益，先检查已有结果里的队列/缓存
  条件，不能通过反复换压力点寻找漂亮百分比。
- 正向结果需要交替重复对照，观察离散性；目标是完整轨迹墙钟至少下降
  10%，完成率不降，轨迹 P95 无实质恶化。未达到不推荐写进简历。
  10% 是本项目投入阈值，不是提前承诺。
- 报告固定请求的生成 token hash 差异和 corrupted/失败信息。不同 batch
  可能改变数值；回放完成率不能替代 Agent 的任务正确率验证。

## 实现边界

初筛补充决定：0.6B 上 30s 阈值降低整批耗时约 16%，但冷首轮 P95
从约 8.7s 增至 14.0s；默认 0.5s 的收益较小。基线排队 P50 为 1.65s、
P95 为 4.11s，因此只增加一个由该分布决定的 2s 阈值对照，寻找吞吐和
冷请求等待的折中。后续使用原生建议的 OMP_NUM_THREADS=1，重新运行
相同线程设置的基线；不能和前面的 4 线程结果混合计算收益。

初筛 FCFS 使用同一 fork 的原生调度类，评分扩展未启用。正式确认另建
完全未修改的 v0.29.0 worktree（98dff2a81d747d1dba01a47f939f48c3526d4206）
作为基线，复用同一套已安装的预编译依赖。避免把同一 fork 中关闭功能的
路径，含混表述为整个仓库没有任何修改。

跨模型规则（在 4B 首轮前固定）：先取原版基线的请求排队时间中位数，
向上取整到秒作为候选让行阈值；0.6B 因而是 2s。4B 不盲目照搬小模型的
秒数，也不在观察候选收益后再挑阈值。原作者 30s 仅保留为初筛对照。

新调度器只在现有 AsyncScheduler 前调整有界等待队列。真实本地前缀命中、
近期 session_id、队首等待阈值共同约束候选。未被调度的提前请求恢复位置。
我们修正了非队首恢复/阻塞请求被越过的问题，并让只读缓存长度查询遵守
已有 prompt_logprob_positions 的因果边界。

回放直接通过 AsyncLLM.generate(session_id=...) 进入真实 EngineCore。
原生 OpenAI serving 也将解析出的 session_id 传给 generate，但旧版 SkyRL
代理能否完整传递仍是训练集成边界，不能把直接引擎验证说成训练链路已接通。

## 已遇到的问题

- 上游 patch 的测试 helper 多了本地基线没有的 scheduling_policy 参数；
  只适配 helper，未整体升级基线或全量编译 CUDA。
- git bundle 使用 HEAD 作为导出引用，初次按分支名拉取失败，改为 HEAD。
- 新 worktree 不包含被 Git 忽略的 wheel 扩展和 vendored Python 文件。
  最初 pytest 缺 FA2 扩展，启动引擎又缺 FlashMLA shim；在专用目录内
  复用已有预编译资源，不修改系统包或原实验源码。
- 默认测试模型可能联网查询；使用本地生成的 OPT 配置重定向，开启
  HF_HUB_OFFLINE。118 项调度/缓存测试通过；补充 CLI 与因果边界检查
  27 项通过（189 项因选择条件未执行）。
- 本地数据准备的隔离环境缺 jinja2，补充该依赖后完成冻结。首次提交
  被格式和循环闭包绑定检查拦截，修正后通过所有适用 hook。
- 4B 目录最初只有元数据和不足 1GB 的分片片段。实验机下载与 SSH
  传输速度较慢；本地完整权重已按固定 SHA 验证，记录中断的传输和
  官方 resolve 下载尝试。远程完整哈希确认前不运行 4B。
- 一次源码读取使用错误的工作目录，纠正路径后读取；没有因此修改文件。

## 复核入口

准备数据依赖：uv 管理的 Python 3.12、transformers、pyarrow、jinja2。
`prepare_workload.py --source` 指向已有 code_localization 工作负载目录，
`--output` 必须是新文件。`replay.py` 拒绝覆盖结果；逐请求记录时延、
缓存命中、生成 hash，逐轨迹记录完成耗时，还保存原生引擎统计。
源文件、任务输入和实际权重均记录哈希；启动/JIT 时间单列。

完整 GPU 环境仍由已有 `run-in-workspace.sh` 约束到实验专用目录。
不保存登录凭据，不安装系统驱动、不停止其他用户进程。
